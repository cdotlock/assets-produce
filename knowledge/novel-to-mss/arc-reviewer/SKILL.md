# Arc Reviewer — 弧线叙事外科审查

## 这个 skill 解决什么问题

`episode-writer-reviewer` 是**集级别**工具：它审查一集的格式、语法、节奏和人设，但看不到跨集问题。

弧线叙事问题有不同的层次：

| 集级别问题（episode-writer-reviewer 负责） | 弧级别问题（本 skill 负责） |
|---|---|
| MSS 格式错误 | 前集设置的悬念后集没收 |
| 立绘 look 名不合规 | 前后集人物事实矛盾 |
| NARRATOR 人称错误 | 假选择（两集对比才发现结果等效） |
| 单集节奏问题 | brave/safe 代价在玩家视角下不透明 |
| 单集选择设计 | @signal 被触发但 @gate 没有对应条件 |

**本 skill 只做弧级别问题。集级别问题已由 episode-writer-reviewer 处理完毕。**

---

## 执行原则：理解 → 判断 → 最小干预

**理解**：通读所有集，建立完整的弧线清单（事实、信号、承诺、选择）
**判断**：识别真实问题，区分"真问题"和"可以留给下一弧线处理的事情"
**最小干预**：处方优先删 > 改 > 加；单个处方新增内容上限 10 行

> **10 行硬约束**：如果修复一个问题需要超过 10 行新内容，说明处方找错了根本原因。要么找更小的切入点，要么标记为"需要人工重写"，不要硬塞内容。

---

## 两阶段强制流程

```
Phase 1（诊断）
  主 agent → 准备输入 → spawn 独立诊断 sub-agent
  诊断 sub-agent → 通读所有集 → 输出处方清单（arc-review-prescriptions.md）
  主 agent → 把处方清单报告给用户
  ★ 在用户审批之前，不做任何文件修改 ★

Phase 2（执行）——仅在用户明确批准后开始
  主 agent → 逐项执行批准的处方
  每项执行前 → 读取该处方涉及的周围 15 行上下文
  每项执行后 → 验证修改是否自然融入，不破坏相邻内容
  发现执行结果不对 → 停止，上报，等待指示
```

---

## 输入

- **弧线集数文件列表**：所有该弧线 `ep_N_final.md` 的完整路径（按顺序）
- **弧线类型**：`common`（公共线）或 `route/{li-name}`（LI 路线）
- **Character Bible**：`02-character-architect/` 下对应角色的 bible（用于人设一致性验证）
- **弧线 Plan**：`03-entity-planner/` 下对应弧线的规划文档（用于验证 @signal / @gate 设计意图）

---

## Phase 1：诊断（主 agent 的职责）

1. 用 `Glob` 确认所有集文件存在
2. 用 `Task` spawn `general-purpose` 诊断 sub-agent，prompt 包含：
   - 所有集文件的完整路径列表（按顺序）
   - Bible 路径 + Plan 路径
   - 下方的"诊断协议"全文
   - 输出路径：`scripts/arc-review-prescriptions.md`
3. sub-agent 返回后，主 agent 读取处方清单，完整汇报给用户
4. **等待用户审批**，未收到明确批准不执行任何修改

---

# 诊断协议（主 agent 喂给 Task sub-agent 的 prompt）

你是 `{弧线名称}` 的叙事外科医生。你的任务分两步：

**Step A（建立库存）**：通读所有集文件，建立弧线清单。
**Step B（诊断开方）**：识别问题，为每个真实问题写一个最小干预处方。

在读完所有集之前，不要开始写任何诊断内容。

---

## Step A：建立弧线库存

按顺序读完所有集文件后，建立以下 6 张清单：

### 清单 1：人物事实表
每个已在剧本中建立的角色事实，格式：
```
角色名 | 事实内容 | 建立于 (E集/Beat) | 后续引用 (E集/Beat，无则"未引用")
```

### 清单 2：承诺 / 兑现日志
每个在剧本中"许下的叙事承诺"（悬念、未解答的问题、暗示的信息），格式：
```
承诺内容 | 建立于 (E集/Beat) | 兑现于 (E集/Beat，未兑现则"未收") | 兑现质量（"充分"/"不足"/"未收"）
```

### 清单 3：Signal 追踪表
所有 `@signal` 触发记录，格式：
```
SIGNAL_NAME | 触发于 (E集/Beat) | 对应 @gate 条件 (E集，无则"孤信号") | 是否有对应 @butterfly 记录
```

### 清单 4：选择质量矩阵
所有 `@choice` 块，格式：
```
位置 (E集/Beat) | 选项A结果 | 选项B结果 | 是否真实有差异 | brave/safe代价是否对玩家透明
```

### 清单 5：集间钩子评估
每两集之间的衔接，格式：
```
E集→E集 | 上集结尾意象/问题 | 下集开头接入方式 | 衔接质量（"流畅"/"断层"/"可接受"）
```

### 清单 6：LI 行动性分布
每个 LI 在每集中的"行动性"（主动行动 vs 被动在场），格式：
```
LI名 | E集 | 行动类型（"主动"/"被动"/"缺席"）| 情感累积效果
```

---

## Step B：诊断与开方

基于 Step A 的 6 张清单，识别以下类型的问题：

### 问题分级标准

**P0（阻塞）**：玩家会感到被骗或困惑，必须修复才能上线
- 硬性事实矛盾（前后集信息不一致）
- 孤信号（@signal 触发但 @gate 无对应条件）
- 明确的假选择（两个选项在叙事上结果等效，而非仅代价不同）

**P1（严重）**：影响体验，强烈建议修复
- 承诺未兑现（悬念设置后彻底消失）
- brave/safe 代价对玩家不透明（玩家选 safe 收到惩罚但没有任何信号告知）
- 集间断层（上集结尾意象与下集开头的情感逻辑割裂）
- 预埋的内容放在了情感氛围不匹配的场景里

**P2（优化）**：不影响上线，修了更好
- 某个 LI 的行动性过低，导致弧线末尾的表态显得突兀
- 某段信息在更合适的位置就位

**不是问题（明确说明）**：
- "这个悬念在后续弧线处理" — 公共线的部分问题留给 LI 路线解决是合理的
- "这个 LI 的魅力积累不足" — 如果这是 LI 路线要处理的，不是公共线的责任

---

### 处方格式

每个问题对应一个处方，格式严格如下：

```
### 处方 N：[一句话问题描述]

**问题分级**：P0 / P1 / P2
**问题类型**：[事实矛盾 / 孤信号 / 假选择 / 代价不透明 / 集间断层 / 承诺未兑现 / 预埋位置错误 / 其他]
**位置**：E集 / Beat / 具体行（引用出问题的原文）

**根本原因**：
[一句话说明为什么会有这个问题——是设计盲点、执行失误还是结构性矛盾]

**处方**：
[具体操作：增/删/改 + 位置 + 内容]

操作类型（选一个）：
- 删除：[引用要删除的内容]
- 修改：[引用原文] → [修改后内容]
- 新增：[在 XX 之后/之前，新增以下内容]

**新增内容行数**：N 行（必须 ≤ 10）
**理由**：[一句话，说明为什么这个处方能修复根本原因而不是症状]

**不要做**：[明确说明执行时不能做什么，防止 scope creep]
```

> **如果一个问题的处方超过 10 行新内容**，不要强行开方。改为：
> ```
> **处方**：需要人工判断
> **说明**：[描述问题，说明为什么没有小于 10 行的干净修复]
> ```

## Phase 2：执行（仅在用户明确批准后）

主 agent 按以下流程逐项执行批准的处方：

### 执行协议

**每个处方独立执行，不批量操作。**

**执行前**：
1. 读取目标文件中处方涉及位置的**前后各 15 行**
2. 确认上下文的情感氛围、人称、节奏与处方内容匹配
3. 如果发现不匹配（比如新增内容的情感基调与周围场景冲突），**停止**，向用户报告，不执行

**执行中**：
- 删除操作：精确引用，不多删一行
- 修改操作：只改指定内容，不改同行其他内容
- 新增操作：注意空行规范（YOU 行之间空行，@命令独占行）

**执行后验证**：
1. 读取修改后的前后各 15 行，确认：
   - 语法：YOU / CHARACTER / NARRATOR / @命令格式正确
   - 融合：新内容与周围内容节奏一致，读起来不像"插入物"
   - 不引入新问题（比如新增的 YOU 行里有 NARRATOR 应该避免的 she/her 代指 MC）
2. 向用户报告：处方 N 已执行，位置 [XX]，验证通过 / 发现问题 [描述]

**发现任何问题**：停止执行当前及后续处方，向用户报告，等待指示。不自行决定"换个方式继续"。

### 执行顺序

P0 → P1 → P2

同级别内，按集数顺序（E1 → E8）执行，避免后执行的处方依赖未执行的前置。

## 使用示例

```
用户：请对 no-rules-in-bad-ideas 公共线运行 arc-reviewer

主 agent 执行：
1. 确认 ep_1_final.md 到 ep_8_final.md 全部存在
2. 读取 Character Bible 路径和 entity-planner 路径
3. 组装诊断 prompt，spawn 诊断 sub-agent
4. 等待 sub-agent 输出 arc-review-prescriptions.md
5. 向用户展示完整的处方清单
6. 等待用户指示（"批准全部"/"批准 P0+P1"/"修改处方 3"等）
7. 按批准范围逐项执行

用户审批格式示例：
  - "全部批准" → 执行所有处方
  - "批准 P0，P1 等下再说" → 只执行 P0 处方
  - "处方 3 不对，删掉那行就够了" → 修改处方 3 后执行
  - "处方 5 不执行，其他全批" → 跳过处方 5
```

---

## 禁止事项

- **Phase 1 诊断 sub-agent 不能修改任何文件**，只读和写处方清单
- **Phase 2 执行不能在用户批准前开始**，哪怕处方看起来显然正确
- **执行前不读上下文直接 Edit** — 必须先读 ±15 行
- **批量 Edit 多处** — 每个处方是一个独立的 Edit 操作
- **处方超出 10 行新内容时强行执行** — 标记为"需要人工判断"
- **把"LI 路线应该处理的问题"列为公共线 P0** — 弧线边界要清晰
- **把已存在的集级别问题（格式、look 名）列为弧级别问题** — 这是 episode-writer-reviewer 的职责范围
